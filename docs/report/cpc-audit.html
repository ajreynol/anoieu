What this is

anoieu reads a Eunoia signature the way ethos does not: eagerly, without a proof in hand, and asking about every declaration rather than only the ones a proof happens to exercise. This is the first audit it has run. Everything below was confirmed by building the smallest signature that reproduces it and running ethos on that.

Of the 23 witness files in the tool's own suite — each one holding a single, deliberate mistake — ethos accepts 19 and answers correct. It refuses four: a declare-rule field out of order, an opaque argument after an ordinary one, a program case of the wrong arity, and a pattern with two :list parameters.

Findings

ErrorFinding 1· programs/Strings.eo:42, :55·EO0064

Two programs declare a return type their cases never produce

(program $is_seq_const_rec ((T Type) (e T) (ss (Seq T) :list))
  :signature ((Seq T)) Int                                  ; declares Int
  (
  (($is_seq_const_rec (seq.++ (seq.unit e) ss))  ($is_seq_const_rec ss))
  (($is_seq_const_rec (as seq.empty (Seq T)))    true)      ; returns Bool
  (($is_seq_const_rec ss)                        false)     ; returns Bool
  )
)

Every case returns a Boolean. The docstring above it says “return: true if s is a sequence constant.” The signature says Int. $is_seq_const, immediately below, repeats the mistake. Program bodies are not type checked — the user manual says so outright — so ethos accepts both.

Whether this bites depends entirely on where the programs are called, and today every call is inside an eo::requires, which compares by evaluation and never asks for a type. The calculus works. The trip-wire is the first call anywhere a Bool is expected:

$ ethos t.eo          ; (and ($is_const x) true)
Error: Type checking failed: Checking application of and
  Term: ($is_const x)   Has type: Int   Expected type: Bool

The error names neither the program nor its declaration. The defect also travels downstream unchanged: the same three findings appear in logos/install/defs/Cpc.eo and Cpc.cached.eo, the flattened copies the Lean development is built from.

Fix: :signature ((Seq T)) Bool on both programs.

WarningFinding 2· expert/theories/ArithExt.eo:17–20, 26–29·EO0031

Four skolem declarations are duplicated verbatim

; skolems for virtual term substitution
(declare-const @arith_vts_delta Real)
(declare-const @arith_vts_delta_free Real)
(declare-parameterized-const @arith_vts_infinity ((T Type)) T)
(declare-parameterized-const @arith_vts_infinity_free ((T Type)) T)

The block appears twice, nine lines apart, comment included. Ethos reads a repeated declaration as an overload, so these are two distinct symbols that print identically. Nothing is wrong today: the second copy shadows the first before any term is built from it. What the duplication sets up is the worst diagnostic available —

Error: Unexpected conclusion for rule refl:
    Proves: (_ (= d) d)
  Expected: (_ (= d) d)

— a proof failure whose two sides are the same text. Anything later that builds a term with one of these symbols between the two blocks turns the duplication into that.

Fix: delete the second block.

ErrorFinding 3· ethos/tests/match-simple.eo:11·EO0040

A right-associative operator that cannot fold

(declare-const < (-> Int Int Bool) :right-assoc)

A right-associative operator puts its own result back where its second argument stood, so its type has to be (-> T1 T2 T2). This one takes an Int and returns a Bool, which makes every application of three or more arguments ill-typed:

Error: Type checking failed: (_ (< 1) (_ (< 2) 3))
       Checking application of (< 1): unexpected type of child #1

The test only ever applies < to two arguments, so the attribute has been inert since the file was written. This one is in the ethos tree rather than in CPC, but it is the same family: an attribute whose contract nothing checks.

Fix: drop the attribute, or give the operator a foldable type.

One that is only a bug from the wrong entry point

$evaluate_list is forward-declared in programs/Utils.eo:70 and defined in Cpc.eo:347, so a run whose entry point is expert/CpcExpert.eo alone has it declared and never defined — under SMT-LIB a free uninterpreted function, under Lean a name that was never written. In practice cvc5's regression runner writes the two includes in order (test/regress/cli/run_regression.py:372), so the pair always loads together and the gap never opens. The check now says “under this entry point” for exactly this reason.

How much of this survived scrutiny

Every check reported false positives on CPC when it was first written, and each fix was a statement about what Eunoia means rather than about the code. The record matters more than the count, because it is what makes the surviving findings worth reading.

The check first assumedCPC's answer
a right-associative operator's return type equals its second argument typeconcat : (-> (BitVec n) (BitVec m) (BitVec (eo::add n m))) is fine — compare type constructors, not terms
a type is what it is written asString is a define for (Seq Char), @re.empty for (str.to_re "") — expand aliases first
a symbol's return type is what its declaration saysite : (-> Bool A A A) says nothing until the arguments say what A is — bind the callee's type parameters, and stay quiet if any is left unbound
any two different type heads disagreeT, U, S are variables — compare only heads that resolve to a declared type constructor
a program matching an n-ary application needs a case for the nil$get_zero matches (or b1 b2) to say what or's unit is, and walks nothing — require a recursive call on the tail, unguarded
an uncovered nil is a findingmost nils in CPC are non-ground, and each instance spells its base case differently — say nothing when the nil is non-ground

Reproducing this

python3 tools/sweep.py <ethos>/tests <logos>/install/defs <eudaimonia>/examples
ETHOS=<ethos>/build/src/ethos python3 tests/run.py --oracle

The last command is the one that says whether a finding is news: it runs ethos over every witness in the suite and prints its verdict beside anoieu's.

anoieu is a static analyzer for Eunoia signatures (*.eo) and semantic configuration sets (*.eos). It does not look for soundness bugs — whether a rule is valid is what the verification conditions ethos-eoc emits are for. Its question is the one below that: whether a signature and its semantics say something coherent at all.

Not yet built: the full type checker (a rule that may conclude a non-Bool term through a program's cases), and the triple — signature against calculus semantics against SMT semantics — which is where the :is-list-nil and exclusion-closure gaps live.
